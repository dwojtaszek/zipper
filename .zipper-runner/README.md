# Zipper Autonomous Runner

This directory contains the autonomous runner pipeline that manages GitHub issues, triggers the AI agent, and creates pull requests.

## Operating contract

Run from the repository root:

```bash
.zipper-runner/cron-wrapper.sh --agent droid
.zipper-runner/cron-wrapper.sh --babysit-only
python3 .zipper-runner/runner.py --status --agent droid
```

`--agent` prefers that agent for this run only, ahead of other priority tiers. Disabled models (priority 0) and unhealthy agents remain excluded; normal fallbacks remain available. It does not edit `AGENT_PREFERENCES.md` or timers. Configuration precedence is command-line agent preference, process environment, ignored `.env`, then defaults. Existing environment values, including empty values, are preserved.

Agent health probes run only when a coding mission is needed, or during `--status`; idle babysitting and green-PR merge evaluation need no agent credits. `--dry-run` skips health calls. Babysit-only, capacity reached, and no eligible issue each have distinct logs; only issue directories count toward capacity.

After successful intake, the runner immediately evaluates the PR through the existing CI, WIP, local CodeRabbit, and robot-review gates. Pending checks remain pending, not failures. CodeRabbit's successful zero-finding review may be reused within the same runner process only for a clean, unchanged `HEAD` and `main`; a changed commit or base requires another review. After a merge, clean local `main` fast-forwards immediately. Dirty, divergent, or non-main repositories are preserved and sync is deferred.

Automatic actions additionally fail closed on PR authorization. Active, orphan, and Dependabot merge paths share one guard: an open, non-draft PR into this repository's `main`, a same-repository head, and a well-formed head SHA. Runner-created work records the PR number and branch in its issue state and requires a `TRUSTED_AUTHORS` author; authorization is bound to that PR, not to a frozen SHA, so a head that moved past the recorded `authorized_head` stays authorized. The maintainer is the sole merge maintainer and GitHub forbids approving your own pull request, so demanding an unchanged head would strand their own PRs after any rebase or force-push. Any other origin needs an explicit `APPROVED` review of the current head from `MERGE_MAINTAINERS` (default `dwojtaszek`, separate from intake authors). Forks are never automatically merged or recovered. Dependabot is identified by REST account ID `49699333`, login `dependabot[bot]`, and account type `Bot`, never a `dependabot/` branch prefix. Every contributing commit must have verified signed bot authorship and a bot or GitHub web-flow committer; the commit listing must end at the current head. Mixed, unsigned, or changed bot heads require exact-head maintainer approval. Orphan recovery requires an issue reference and the same authorization before fetching/creating a worktree. Existing local branches are not replaced.

After review, the runner rechecks authorization, head, and successful CI, then merges with `--match-head-commit` and without `--admin`. Branch protection remains authoritative. A head that moved after review is refused and re-evaluated on the new head; green CI alone never authorizes execution or merge.

A rewritten remote head is handled by the recorded `authorized_head`, not by authorization: when that record no longer names the reviewed head, the worktree's local tip is the head the rewrite abandoned rather than an unpublished completion, so the runner pins any local-only commit on a backup branch and blocks for a human, or, when there is no local-only work and the tree is clean, follows the rewrite. Reading the abandoned tip as unpublished instead would push the content straight back over a force-push. A record that stores no head (a legacy record, or one whose local branch no longer resolved when it was written) cannot tell the two apart, because a head the runner published and a head a rewrite abandoned look identical locally; that case resolves toward inaction, so the worktree resumes through the agent and nothing is republished.

A PR the runner cannot authorize — it was converted to a draft, its base was retargeted off `main`, its head branch was renamed, or its provenance is unverifiable — keeps the runner's single worktree slot and is never acted on: `_authorized_pr` fails closed, and no repair missions are dispatched for it. The runner sends a rate-limited email naming the concrete reason, the recorded head, the current head, and the remediation that works for that reason. The email is deliberately not sent when the PR simply could not be read, so a `gh` outage cannot raise a false alarm, and a contributor PR that merely mentions an issue number is suppressed by the record check. Deleting the issue state is never offered as a fix: provenance is read from that state, so removing it would leave the PR unauthorized permanently. A PR the runner holds work for but has no record of — state never written, or the record belongs to a different PR — is reported the same way instead of being skipped silently.

A green PR the runner has no authorization record for is never evaluated by the orphan scanner, so nothing would ever merge it. Two shapes hit this: a PR whose branch, title, and body carry no issue reference (PR #1258 sat green and unmerged for four days), and a PR that names an issue the runner never recorded work for. After `RUNNER_STALLED_PR_HOURS` (12 default) the runner sends a rate-limited email naming the PR and the remediation. It never merges such a PR on its own: an unverifiable origin stays fail-closed.

The orphan scanner can also stall on a PR it *can* authorize: when the review gate is unsatisfied, a merge keeps failing, or CI is red, it recreates a worktree to babysit the PR. If that recreation fails — a local branch parked at a different head, a fetch mismatch, or a failed worktree add — the PR used to be skipped every cycle with no signal. It now sends a rate-limited `Cannot Be Babied` email naming the PR and branch, so the operator can reconcile the local branch by hand. A successful recreation stays silent, because the runner then babysits the PR normally.

An open PR with a WIP checkpoint resumes its existing worktree through the normal agent completion path, once per worktree per invocation. Failed continuations preserve uncommitted work; dry-run never dispatches a continuation. All existing-PR repairs validate and commit locally without pushing or importing another remote PR head. The runner checks the captured authorized remote head, a clean descendant completion, and the committed local CodeRabbit gate, then rechecks authorization immediately before publication. It publishes that exact completion SHA using an atomic lease against the captured remote SHA. The ancestry check permits only fast-forwards; the lease does not authorize history replacement. Provenance advances and a prior blocker clears only after that publication succeeds. Failed review or publication preserves the local commit and records the blocker for a later retry. Initial runner-created PR provenance records the published PR SHA, not an unpublished local checkpoint. Interrupted mission progress retains a separate `local_head` with `completion_ready: false`; it resumes through the agent without discarding dirty edits. Only publication requires a clean tree. Initial review failure exits intake, so further repair uses the captured-head babysitter instead of the old push-enabled intake prompt. A local-only commit is not PR progress. A completion commit must represent actual finished work, not a renamed checkpoint or empty commit. Readiness still depends on existing CI and reviews, with advisory Jev verification; a tree diff alone cannot prove semantic completion. Progress checks take read-only thread snapshots; the full robot-review wait remains a merge gate, not a delay before or after each repair.

Droid uses `stream-json`, drains stdout and stderr concurrently, and logs assistant-progress markers plus a 60-second heartbeat. Prompts, message text, tool arguments, and results are not echoed into live logs. The plugin still returns `(exit_code, stdout, stderr)`, with stdout containing final assistant text (partial assistant messages on interrupted runs), not raw tool payloads. The 45-minute mission timeout still terminates the process group; droid keeps that longer bound because it streams `assistant progress`, so a shorter wall-clock cut would truncate a working mission rather than a hung one.

### Cadence

The recommended schedule is intake every 15 minutes and babysitting every 5 minutes. The existing runner lock and one-worktree limit remain authoritative. A successful intake does not start a second issue in that invocation.

- **Cron:** run `bash .zipper-runner/setup-cron.sh`. It migrates the exact legacy six-hour intake entry, preserves custom schedules and unrelated jobs, and adds babysitting if absent.
- **Existing systemd user timers:** after the PR is merged, install the checked-in timer drop-ins:

```bash
mkdir -p "$HOME/.config/systemd/user/zipper-intake.timer.d" "$HOME/.config/systemd/user/zipper-babysit.timer.d"
cp .zipper-runner/systemd/zipper-intake.timer.d/cadence.conf "$HOME/.config/systemd/user/zipper-intake.timer.d/"
cp .zipper-runner/systemd/zipper-babysit.timer.d/cadence.conf "$HOME/.config/systemd/user/zipper-babysit.timer.d/"
systemctl --user daemon-reload
systemctl --user restart zipper-intake.timer zipper-babysit.timer
```

Use one scheduler, not both. Committing the drop-ins does not change live timers; installing them replaces the calendar cadence while preserving existing service paths and persistence settings. Note that the bare `OnCalendar=` in each drop-in clears the base unit's **monotonic** timers as well as its calendar cadence, so a base unit's `OnBootSec` stops taking effect. That is not a loss here: the host's intake and babysit units set `Persistent=yes`, so a run missed while the machine was down fires as soon as the timer is active, which is what the boot timer was standing in for.

Install **both** drop-ins together. The intake timer and the babysit timer are independent units, so installing one and forgetting the other leaves no error anywhere: the host keeps a working runner that simply loses new-issue pickup for the rest of each calendar window. Verify the live cadence after installing, and treat a stale intake interval as a deployment bug rather than a scheduler quirk:

```bash
systemctl --user show zipper-intake.timer -p TimersCalendar
systemctl --user list-timers zipper-intake.timer zipper-babysit.timer --no-pager
```

A 15-minute intake answers a structural gap rather than load: each intake firing is a single instant, so one long mission occupying the only worktree slot at that instant costs the whole interval until the next firing. Frequent firing lets the existing lock and worktree limit decide, instead of the schedule.

Both drop-ins name UTC in their `OnCalendar` (`*:0/15 UTC`, `*:0/5 UTC`). A bare spec is read against the local clock, which repeats an hour at the autumn DST fall-back and stops every timer for that hour. Each drop-in also clears the cadence list (`OnCalendar=`) before assigning its own, which is what makes it replace the base unit's cadence rather than merge with it. See [Deploying merged changes](#deploying-merged-changes) for the measurement.

### Locks

Four locks, each guarding a different thing. Confusing them is what starved babysitting.

| Lock | Path (default) | Held by | Held for |
|------|----------------|---------|----------|
| Intake | `.zipper-runner/runner.lock` (`LOCK_FILE_PATH`) | an intake run | the whole run, including its agent mission |
| Babysit | `.zipper-runner/babysit.lock` (`BABYSIT_LOCK_PATH`) | a babysit pass | that pass only |
| Main checkout | `.zipper-runner/repo-mutation.lock` (`REPO_MUTATION_LOCK_PATH`) | either process | one git mutation of the main checkout |
| Worktree mission | `state/worktree-<name>-mission.lock` | either process | one agent mission in that worktree |

The babysit lock is separate from the intake lock on purpose. `zipper-babysit.timer` fires every 5 minutes, and an intake run holds the intake lock for the 20-42 minutes its mission takes, so while babysit shared that lock **67% of the last 60 babysit firings did nothing** (47 of 235 overall) — they waited out `RUNNER_LOCK_TIMEOUT` and exited. A babysit pass is bounded work on an existing PR, so it takes the babysit lock instead and runs alongside an in-flight mission. An intake run also babysits; it takes the babysit lock only around its own pass and releases it before it starts a mission, or every babysit firing during that mission would skip again.

Both processes still take the main checkout lock around the git mutations that touch the shared checkout, and defer their mutation when they cannot get it. That is what protects the checkout; the intake and babysit locks only decide *who runs*, not *who may touch the tree*. Each lock has its own heartbeat (`<kind>-heartbeat.json`), so one kind's stale-lock watchdog can never judge, or kill, the other kind's holder. `runner.py --status` reports these three by name, and the worktree mission lock below per worktree.

Because the babysit lock is non-blocking (`BABYSIT_LOCK_TIMEOUT`, 0), a firing that finds another babysit already running exits immediately and the next firing retries in 5 minutes, rather than queueing behind it.

The **worktree mission lock** is the one the other three do not cover. The intake and babysit locks decide who runs, but nothing stopped two runs from driving the *same worktree*: an intake mission implements an issue while a babysit firing picks the same worktree up and resumes it. Both agents then edit the same files and commit to the same branch, so one side's work is overwritten or its commit orphaned while both report success. Measured on the host, 3 of 318 completed runs had an intake and a babysit mission in one worktree at the same time, one pair overlapping for 40 minutes.

Every agent mission now takes this lock for its duration, and a run that cannot get it leaves the worktree untouched for the run that holds it. It is non-blocking for the same reason the babysit lock is: a mission runs for tens of minutes and the caller's own cadence retries within minutes, so skipping costs one cycle while waiting would hold an entire run open.

It is **reentrant within one process**, like the main checkout lock and for the same reason: an intake run babysits its own worktree as soon as its mission returns, so the holder must be able to re-enter its own lock. `flock` is per open file descriptor and refuses a second `open()` even from the process that already holds it, so without that check the run's own babysit pass would skip the PR it had just published and log "another run" that does not exist.

The lock file is exempt from the `state/` age sweep (`_prunable_state_file`). `open(path, "a")` does not advance a file's mtime, so an old lock file stays old forever and the sweep would delete it every run. Deleting a *held* lock does not release it — the inode lives on — but the next acquire creates a fresh inode that a second process can lock, leaving two runs both convinced they own the worktree.

It is deliberately **not** wired to the `_reclaim_stale_lock` watchdog, which reclaims by killing the holder's process group; that would kill a whole intake run for a worktree it is merely borrowing. Because it therefore has no heartbeat and no reclaim path, `runner.py --status` prints the recorded holder (`pid` and how long it has been held) beside each worktree, so a wedged holder is visible instead of looking like an idle worktree. The recorded pid is what says whether removing the file is safe.

Two limits are worth stating plainly, because the lock is narrower than "this worktree is exclusive":

- **The holder is the runner, not the work.** `flock` is released when the holder dies, and the agent runs in its own session, so a runner killed outright (OOM, `kill -9`) frees the worktree while its agent is still writing. The watchdog does not cover that case either, since it reclaims by killing the holder's process group and the agent's separate session escapes it. What keeps the window small is that every plugin bounds a mission: 900s for the four agents that hang silently (opencode, hermes, codex, claude), and 2700s for the two that report liveness or stop themselves (agy, droid). A systemd stop is safe: it kills the whole control group, agent included.
- **Missions are not the only thing that touches a worktree.** The pre-PR CodeRabbit check, PR creation, the orphan-PR branch checkout, and worktree removal run without this lock. The lock serializes *agent missions*, which is the hazard that was measured; it does not make a worktree generally exclusive.

### Deploying merged changes

The runner syncs its own checkout (`sync_main_repo`) only while it holds the lock, and it holds the lock for the whole of a long agent mission. A merged change therefore waited for the next lock-winning run before it went live, which is tens of minutes when intake is busy. Deploy is a fast-forward of a checkout that is supposed to sit on `main` and stay clean, so it does not need to wait for a run; it only needs to not collide with one.

`deploy-main.sh` runs on its own one-minute timer, outside the runner lock:

```bash
install -Dm755 .zipper-runner/deploy-main.sh "$HOME/.local/bin/zipper-deploy-main.sh"
install -Dm644 .zipper-runner/systemd/zipper-deploy.service .zipper-runner/systemd/zipper-deploy.timer \
    "$HOME/.config/systemd/user/"
systemctl --user daemon-reload
systemctl --user enable --now zipper-deploy.timer
systemctl --user list-timers zipper-deploy.timer --no-pager
```

Install the script **outside** the checkout, as above. A copy inside the tree is an untracked file in the very commit that adds it, so the first fast-forward carrying it would refuse to run and deploy nothing. `REPO_PATH` in the service unit points at the checkout; the script derives nothing from its own location when `REPO_PATH` is set.

The timer pins `AccuracySec=1s`. systemd's default accuracy is one minute, which is this timer's entire cadence, so a tick may fire up to 60 seconds after its scheduled elapse. A one-minute cadence cannot tolerate a one-minute slack, so the accuracy is stated rather than inherited. `.zipper-runner/tests/test_timer_units.py` guards the rule for any timer whose cadence is under five minutes, so a future short-cadence timer cannot silently inherit the default.

Two things about that default are worth stating precisely, because the obvious reading is wrong in both directions.

**The observed lateness is what prompted the change, not what proves it.** Measured on the host, ticks landed at seconds 50, 53, and 56 rather than 0, and intervals of 113s appeared where 60s was promised. An A/B settled it: with the default accuracy, a clean run of 28 ticks put every tick on second 0 with all 27 gaps at exactly 60s and **zero** gaps over 65s; with `AccuracySec=1s`, 162 ticks over three hours in production showed the same 113s gaps as before. Those gaps occur at 00:40, 01:30, 01:35 and 01:54 — exactly the manual `systemctl restart`s taken during the experiment. They were self-inflicted. The change stands on the argument above, which is a real defect in the unit; it is not a measured fix for the 113s intervals.

**Accuracy does not replay a missed firing.** systemd skips a firing when the service is still active, and `AccuracySec` cannot bring that tick back. The deploy's fetch is bounded at 45s, so a normal run finishes well inside the minute, but a slow fetch plus a slow merge could still overrun it and lose the next tick. A cadence guarantee tighter than that would need the script itself to re-run on completion, not a smaller accuracy.

**A cadence read against a clock that repeats an hour stops the runner for it.** The systemd timers name UTC in their `OnCalendar` (`*:0/1 UTC`, `*:0/5 UTC`, `*:0/15 UTC`). systemd iterates a spec through the wall clock of the zone it names, and that clock repeats an hour at the autumn DST fall-back: after `02:59 CEST` the next local minute is `02:00 CET`, which sorts *before* the minute just fired, so the iterator treats the repeated hour as elapsed and jumps to its end. Measured on the host at the 2026 autumn transition, all three timers went from a last fire of `02:45` (intake), `02:55` (babysit) and `02:59` (deploy) CEST to a next fire of `03:00` CET — a 61-75 minute real-time outage of the entire runner, and it delayed a merged deploy by 35 minutes while it lasted. Spring-forward costs nothing by the same mechanism: the elapses in the missing local hour never existed, so the real-time cadence is unchanged.

The hazard belongs to the spec's zone, not to the host's: pinning a timer to a DST-observing zone such as `Europe/Warsaw` reintroduces the gap even when the host itself is in UTC. UTC has no transition, so its wall clock never repeats or skips. Where the host's offset is a whole number of hours — this host, and most of the world — the local minute alignment is unchanged and `*:0/1 UTC` still fires on the minute. A few zones have a fractional-hour offset (`Asia/Kolkata` +05:30, `Asia/Kathmandu` +05:45, `Pacific/Chatham` +12:45/+13:45), where the firing minutes shift by that fraction. That is harmless: the runner needs a periodic cadence, not alignment to the local clock, so it polls for new work and picks it up on the next firing either way. `TimerTimezoneTests` checks each timer's zone for a repeated hour, checks that a drop-in clears the cadence list it replaces, and guards the classification helpers against the spellings systemd and tzdata accept.

This covers the systemd timers, which are what the host runs. The `setup-cron.sh` path expresses its cadence as a crontab entry instead; cron has no per-entry timezone and its own fall-back semantics, so it is not covered by this change.

The script never discards work: no `reset`, no `checkout`, no `stash`, no `clean`. It does nothing and logs why when the checkout is on another branch, has modifications to tracked files, is mid-rebase/merge/cherry-pick, holds an `index.lock`, or is not a fast-forward. Two of those refusals exist because a merge is not as harmless as it looks: `--ff-only` refuses a diverged checkout instead of creating a merge commit, and `--no-overwrite-ignore` refuses when the incoming commit would overwrite an ignored local file — the tracked-file check cannot see ignored files, and git overwrites them by default, which is how a deploy could destroy the runner's own ignored `runner.lock` or logs. Outcomes land in `.zipper-runner/logs/deploy_*.log`; the already-current case is silent. The runner reads `runner.py` once at process start, so a deploy during a run cannot affect that run.

The script and the runner share one lock around the main checkout's git mutations, and that is what makes deploying safe rather than merely fast. The runner mutates the same checkout, and `_cleanup_git_state` deletes `.git/index.lock` without checking its age, so a run starting mid-deploy would remove the lock an active git process is holding and then run `git rebase --abort` on the same tree. Sharing the runner's own lock would not work: it is held for a whole agent mission, so every deploy would stall for the 20-42 minutes a mission takes. The shared lock is therefore taken only around mutations, never across a mission, so a deploy waits at most one mutation. On the runner side that means the whole-checkout operations — `_cleanup_git_state`, `verify_repo_on_main`, `sync_main_repo`, `_sync_main_after_merge` — take it, and each defers rather than proceeds when it cannot. Narrow ref and worktree operations (branch and worktree creation, the per-branch fetch for an orphan PR) do not take it: they are not the hazard above, and making the runner wait on a lock a shell timer holds would trade a real stall for a theoretical one. The orphan-PR fetch reads its own remote-tracking ref with `--no-write-fetch-head` instead of `FETCH_HEAD`, because `FETCH_HEAD` is a single per-repository file the deploy's fetch also overwrites.

The lock is a directory rather than `flock` because `flock` and `timeout` are GNU utilities absent on macOS, where the runner suite runs in CI. It lives at `.zipper-runner/repo-mutation.lock` (`REPO_MUTATION_LOCK_PATH`) and is gitignored because `_repo_is_clean()` counts untracked files as dirt. Both sides write a `created` timestamp, a `pid`, and an `owner` token inside it, and both judge staleness against the same bound (1200s default, `REPO_MUTATION_LOCK_STALE_SECONDS` / `DEPLOY_LOCK_STALE_SECONDS`), deliberately longer than any single locked command so a legitimately slow mutation is never mistaken for a crashed holder and stolen mid-write. The shell falls back to the directory's mtime when the `created` file is missing, so a holder that died between creating the lock and recording its timestamp is still reclaimable. On release both sides verify they are still the recorded owner, so a holder that lost its lock to a steal cannot delete the thief's lock and admit a third writer.

A recorded `pid` that is no longer running is reclaimed **immediately**, without waiting for the stale bound. Age alone was not enough: a holder killed without its cleanup — SIGKILL, OOM, reboot — left the lock behind, and the runner then deferred every main-checkout mutation for the full 20 minutes, logging `REPO LOCK: main checkout busy for 120s; skipping this mutation` on each run. Measured on the host: after one such kill, four consecutive runs (01:50 to 02:04) each waited 240 seconds and deferred both their main-sync and their branch recovery, and the checkout was left unmaintained for that whole window. The pid check is conservative by construction — an absent, malformed, or unreadable pid, a pid this process may not signal, or the process's own pid all fall through to the age bound rather than stealing a lock that may still be held. On the shell side the check requires `/proc`, because `kill -0` alone cannot separate a dead process from a live one this user may not signal; where `/proc` is absent (macOS) the age bound decides instead.

A **non-directory** at the lock path is reclaimed immediately by both sides, and is not the same case as a stale holder: the protocol is `mkdir`, so a file there cannot belong to any holder, yet every later `mkdir` fails with `EEXIST` and reads as "another process holds it". Measured on the host, twice: a `--status` run created such a file and the deploy timer skipped **every tick for 20 minutes** while the runner deferred its mutations, and a second run did it again for 11 minutes, until the stale bound expired each time. The cause was `_lock_is_held`, which probed a lock by opening the path with `"a"` — harmless for the `flock` locks, but against this directory lock's path it manufactured the file it then mistook for a holder.

The probe now opens **read-only and non-blocking**, so it can neither create the path nor hang on it. Read-only alone would not be enough: `exists` and the open are two steps, and this path is a *shared* lock that other processes remove routinely, so a creating open would recreate the poison file whenever the probe raced a reclaim. Non-blocking matters because opening a fifo for writing blocks until a reader appears, which would hang the diagnostics rather than report. The type is read from `fstat` on the descriptor, so there is no second path lookup to race, and only a regular file can hold a `flock` — `flock` on a fifo fails on macOS with `ENOTSUP` but succeeds on Linux, so trusting it would have made the answer platform-dependent. Note that `--status` is not read-only: `main()` prints the diagnostics and then continues into a normal run, which is why the run that created the file also stalled 120s on the lock. The diagnostic output is read-only; the run is not.

A directory, or a symlink to one, is left alone by the reclaim — that is a real lock, and the normal reclaim path owns it. Anything else at the path is removed, and `os.remove`/`rm -f` refuse a directory, so the check-then-act can never delete a live holder's lock: the holder's `mkdir` remains the only atomic claim and the loser's `mkdir` fails. A symlink is removed as the link it is, never its target. The shell tests `-L` as well as `-e` for that branch, because `-e` is false for a **dangling** symlink: `mkdir` still fails on one, so without `-L` it would read as a held lock and only the age bound would clear it.

The fetch is bounded on every host too. `timeout`/`gtimeout` is used where it exists; where neither does, the fetch runs in the background with a watchdog that kills it. The watchdog is used rather than the tempting `perl -e 'alarm shift; exec @ARGV'`, which is not equivalent: the alarm survives the exec only until the exec'd program is itself a shell script, after which the signal is deferred until that script's foreground child finishes, so the bound silently does nothing. Git's own low-speed abort is the third, weakest layer — it covers a stalled transfer but only for HTTP(S) remotes, so it is a backstop rather than the bound.

To verify it end to end, rewind the checkout and watch the timer restore it. The guard below is deliberately strict, because `git reset --hard` destroys work that a bare `HEAD == origin/main` check does not see: local edits to tracked files (the commit matches, the working tree does not), and any branch that happens to point at `origin/main` (the reset would rewind that branch instead of `main`). A checkout *ahead* of the remote is a state the script deliberately tolerates, so "it looked clean" is not enough to make a reset safe.

```bash
cd ~/repos/zipper
if [ "$(git branch --show-current)" != "main" ]; then
    echo "not on main; refusing to rewind. Use a disposable clone instead."
elif [ -n "$(git status --porcelain)" ]; then
    echo "checkout has local changes; refusing to rewind. Commit or stash them first."
elif [ "$(git rev-parse HEAD)" != "$(git rev-parse origin/main)" ]; then
    echo "HEAD is not exactly origin/main; refusing to rewind."
else
    git reset --hard HEAD~1
    for _ in $(seq 1 20); do                      # a timer may fire up to a minute late
        [ "$(git rev-parse HEAD)" = "$(git rev-parse origin/main)" ] && break
        sleep 5
    done
    [ "$(git rev-parse HEAD)" = "$(git rev-parse origin/main)" ] \
        && echo "deployed" || echo "TIMED OUT: deploy did not run"
    tail -1 .zipper-runner/logs/deploy_*.log
fi
```

### Harness limits

`AGENTS.md` documents bounded tool discovery, native subagent schema mapping, valid GitHub CLI examples, and focused iteration with unchanged final review/test gates. The runner cannot repair Factory's tool catalog, search relevance, or Loop availability. Missing capabilities must be reported rather than retried indefinitely or bypassed against harness policy.

Runner regressions: `cd .zipper-runner && python3 -m unittest discover -s tests`.

### Known limitations

- **`MAX_ACTIVE_WORKTREES` is fixed at 1.** The limit is deliberate: a second concurrent mission doubles the load on one host, and the failure modes of two agents writing the same repository are not yet measured. The friction it causes is real, though — a single long mission is the whole pipeline's throughput, and an unauthorized or stalled PR holds the only slot (see the escalation paths above). The intended next step is a *ramp*: allow a second slot only when the host is demonstrably idle, with a per-slot resource check, rather than raising the constant. Tracked as a future change; do not simply raise the number.

## Unattended endurance

The runner is designed to run for days without human intervention. Every known freeze, crash-loop, flood, and churn path has a bound:

- **Bounded commands:** every `run_cmd` call gets a default timeout (`RUNNER_CMD_TIMEOUT`, 300s; explicit values for longer gates — 25m for the full review-gate wait, 10m for CodeRabbit, and `RUNNER_GIT_NETWORK_TIMEOUT`, 15m, for push/fetch). Git HTTP I/O additionally aborts on stalled transfers (`GIT_HTTP_LOW_SPEED_LIMIT`/`GIT_HTTP_LOW_SPEED_TIME`); operator-configured values always win, and `GIT_SSH_COMMAND` is deliberately not injected so repository `core.sshCommand` stays authoritative. `tests/wait-for-reviews.sh` bounds each of its own `gh` calls (`timeout`/`gtimeout`) because its deadline only fires between polls.
- **Stale-lock watchdog:** each invocation writes a heartbeat for the lock it holds — `state/runner-heartbeat.json` or `state/babysit-heartbeat.json` (pid, pgid, start time). A later cycle that cannot take that lock after its timeout reclaims it by killing the holder's process group once the holder exceeds `RUNNER_MAX_RUN_SECONDS` (12h default) — a wedged run can no longer freeze the pipeline silently. Fail-closed: no usable heartbeat, no takeover. The heartbeat is per lock kind, so an intake run can never be killed on the strength of a stale babysit heartbeat, or the reverse.
- **Process-group cleanup:** all agent plugins launch missions with `start_new_session=True` and kill the whole group on timeout, so orphaned LSP servers or build nodes cannot hold the output pipes (which would block `communicate()` forever while the lock is held).
- **Nested mission timeouts:** an agent CLI with its own print timeout must be told to fire *before* its plugin's kill, or the agent is SIGKILLed mid-turn and its partial work is never reported. agy runs with `--print-timeout 40m` inside its 2700s kill, leaving five minutes to flush output and exit; the earlier 30m value truncated long missions routinely, and a truncated mission still produces a PR that then needs repair cycles. The print timeout is a bound on the *turn*, though, not on the work: agy hands a long command (a test suite, a CI wait) to a background task, its turn then has nothing to do, and it idles out the whole timeout — `root agent idle; waiting up to 40m0s for 1 background task(s)` on its own stderr. Measured on the host: 15 runs did this and returned partial output, 11 of them over 25 minutes, with the work usually already finished; the runner cannot tell, so it re-dispatches next cycle and burns the single worktree slot twice. Lowering the timeout would recover that burn but truncate the runs that legitimately take 32-42 minutes, so both intake prompts instead instruct the agent to run long commands in the foreground and never idle on a background task. The instruction is prompt-level, so it depends on agent compliance rather than enforcing anything; the print timeout remains the backstop.
- **Silent hangs are bounded at 15 minutes.** Four agents give the runner no output until the process exits, so a wall-clock bound is the only thing between a hang and a wasted mission: opencode and hermes run via `Popen` with pipes but log only on completion, codex runs via `subprocess.run` with pipes, and claude writes to a temp file it reads after exit. All four now bound at 900s; 45 minutes was far too long. Measured on the host: one opencode hang logged `Running mission` immediately followed by the kill 45 minutes later with **zero** progress lines in between, inside a 116-minute run that had already burned agy's 40-minute print timeout — the single worktree slot was held for ~85 minutes by agents that produced nothing. agy and droid keep 2700s, because a cut there would truncate a mission that is working rather than one that has hung: agy stops itself via its own `--print-timeout` and reports partial output, and droid streams `assistant progress` (its `Mission active` line is the plugin's own timer, not a liveness signal).
- **What a mission cut preserves.** The worktree and the runner's WIP checkpoint, so file work survives and the next attempt continues from it. Not the agent's conversation context: intake dispatches with `is_continue=False`, so the next attempt starts a fresh session — only the babysit path resumes, and it does so with `--session`, not `--continue`. The runner therefore excludes a WIP-only checkpoint from `work_done`, so an interrupted attempt hands the worktree slot to the next candidate (`_fallback()`) instead of ending the cycle with the slot idle. Note this keys on the branch HEAD, not on why the mission ended: an agent that *succeeded* but left a stray file behind also gets a trailing WIP checkpoint, so its completion is treated as unproven and the next candidate is dispatched. That is deliberate — a completion that still needs a WIP commit has not been demonstrated — but it costs one extra attempt on those issues.
- **gh outage guard:** before a failed `gh pr view` is interpreted as "no PR", the runner proves gh can reach the API (`gh api rate_limit`, free). During network/auth outages the worktree is skipped for the cycle instead of dispatching repair missions on a false premise; one rate-limited alert email is sent.
- **Crash-loop guards:** every `json.loads` on `gh` output is guarded; unparseable output skips the worktree for a cycle instead of crashing identically every 5 minutes.
- **Cross-cycle quota cooldown:** quota exhaustion is persisted in `state/quota-*.json`. When the provider states its own window (`Resets in 85h0m6s`, as agy embeds in its 429 payload), that window is authoritative and recorded as `resets_at`; `RUNNER_QUOTA_COOLDOWN_MINUTES` (60 default) is the fallback for providers that state nothing. The window is read from the provider's **error channel only** — agy reports its 429 on stderr with stdout empty — because stdout is assistant text, including partial text from an interrupted mission, that can quote an unrelated reset and park the model for the wrong span. Retrying inside a stated window can only fail, so honoring it hands the cycle to a working model instead of relaunching a doomed mission every hour for the life of the window. `RUNNER_QUOTA_RESET_MAX_HOURS` (168 default) caps an implausible or garbled hint so it cannot park a model indefinitely, and the marks still expire so silently-reset quotas retry automatically.
- **Worktree mission backoff:** three consecutive fruitless missions on one branch trigger an exponential cooldown (8m → … → 6h cap, `state/worktree-*.json`). Any progress — commits, PR state, thread resolution — clears it; after a served cooldown the ladder restarts low.
- **Blocked-worktree escalation:** a PR the runner cannot authorize never fails silently. The runner sends a rate-limited email naming the concrete reason (draft, retargeted base, renamed branch, missing record) and the remediation that works for that reason, and dispatches no repair missions while the PR stays unauthorized. The worktree keeps its slot, so a human decision is what moves the pipeline again.
- **Missing-model notification:** a model still configured at a non-zero priority that its agent no longer lists is reported once, rate-limited, because the runner otherwise queues it, selects it, and fails the mission at runtime. Only agents whose discovery returned real models are checked, so a provider outage that falls back to `default` cannot name every configured model as missing, and the `default` placeholder itself is never reported because it names the agent's own default model rather than a model discovery can return. A read-only `--status` run prints the warning but sends nothing and spends no rate-limit budget, matching the `All Agents Unhealthy` alert.
- **Unrecorded-PR escalation:** a green PR the runner has no authorization record for — no issue reference at all, or an issue it never worked on — can never be authorized, and the orphan scanner would otherwise skip it forever (PR #1258 sat four days). After `RUNNER_STALLED_PR_HOURS` (12 default) the runner sends a rate-limited `Cannot Be Authorized` email naming the PR and the remediation. It never merges such a PR: an unverifiable origin stays fail-closed.
- **Orphan-recovery escalation:** the orphan path merges without a worktree, so when it cannot recreate one to babysit a PR — an existing local branch at a different head, a fetch mismatch, or a failed worktree add — it sends a rate-limited `Cannot Be Babied` email instead of retrying silently every cycle. A recreation that succeeds stays silent.
- **Environmental gate failures:** a PR blocked by a missing coderabbit CLI (something a mission cannot fix) skips mission dispatch entirely.
- **An absent required check is re-armed, never "fixed".** Branch protection on `main` requires exactly one status context (`ci-gate`, `REQUIRED_STATUS_CONTEXT`). When that context is missing from a PR head's rollup, GitHub treats it as never reported and refuses the merge indefinitely — no diff can change that, because the problem is a status that was never posted. Observed on #1340 (25 Oct): a push produced no `pull_request` workflow run at all while `pull_request_target` runs did fire, so `ci-gate` was never posted and the PR sat `BLOCKED` with every reported check green and zero unresolved review threads. The runner used to respond by dispatching "Fix the blocker and push updates" missions — 40 minutes each, holding the only worktree slot, editing code that was already correct. It now distinguishes *absent* from *failed*: a failed required check is a code problem and keeps the repair path, while an absent one is re-armed by pushing a commit that fires a new `pull_request` event and re-posts the context. The same guard covers the hanging-CI path, because the worst form of this failure — a push that creates no workflow run at all — leaves an empty rollup, which reads as `PENDING`; after two hours the runner used to send an agent to investigate a run that was never created. The re-arm is a best effort, not a guarantee: `perf-baseline-refresh.yml` documents a second cause where a branch pushed with the default `GITHUB_TOKEN` leaves the PR author as `github-actions[bot]` and GitHub holds the run at `action_required`, so a new event creates a new held run (observed on #1187). That shape burns the budget and lands on the rate-limited email, which is why the email reports the reason it could not re-arm rather than asserting the context is unpostable. The re-arm commit is built from the head's existing tree object rather than from the index, so its tree is byte-identical by construction: every gate re-runs against exactly the content that was already reviewed and nothing is bypassed. That construction also matters for safety, because `git commit --allow-empty` commits the *index*, and a failed WIP checkpoint leaves an entire worktree staged — so an index-based re-arm would have published unreviewed agent work under a "re-arm ci-gate" message. Authorization is re-verified before that push (a push is a publication, and a merge failure is the worst moment to assume authorization), which is why the issue number is threaded through: it is what lets the check consult the runner's own record for the PR, and without it only the maintainer-approval path remains — which GitHub forbids on your own pull request, so the maintainer's own PRs could never re-arm. The worktree must be on the PR branch, and the budget is `REARM_MAX_ATTEMPTS` (2) per head — a context still missing after that is not a lost event, so the runner stops pushing and sends a rate-limited `Blocked` email instead. Because each re-arm moves the head, the spent attempt is recorded against the head the push created while carrying the running total forward; deriving it from the new head would hand out a fresh budget every cycle and make the bound unbounded. The count therefore resets only when someone *else* moves the head, and is cleared on merge or close alongside the rerun count. A failed push spends the attempt against the unchanged head too, so a push that keeps being rejected backs off instead of retrying every cycle. The guard only fires on a rollup with no failing check, and only on the snapshot the merge itself was judged against — a merge refused because the head moved, because a check newly went red, or because of a transient API error must not be mistaken for a missing context.
- **WIP checkpoints do not pay the repo gates.** `_auto_commit_wip_checkpoint` snapshots whatever an agent left behind so an interrupted mission loses no files. The pre-commit hook only short-circuits for docs changes, so a `.zipper-runner/**` change ran `dotnet format` plus the full 3,400-test suite — and in a worktree with no build output that means building first, measured at over two minutes on the agent-dispatch critical path. That buys nothing: the checkpoint is never pushed, and the function already fell back to `--no-verify` whenever the hook failed, so unverified WIP commits were always possible. It now skips the hook when *every* uncommitted path is runner-internal; one product file keeps the hook, so a genuinely broken C# state is still caught early.
- **Robot reviewers are optional; the required checks are not.** The merge gate is the required `ci-gate` context (the zipper test suite) plus SonarCloud. Both always run, because they are repository workflows rather than an external app's discretion. The two review bots are neither: CodeRabbit declines this repository outright (public OSS, fewer than 10 stars) and rate-limits itself to a few reviews per rolling hour, and Codex sometimes does not answer at all. The runner reads the gate's machine-readable `REVIEWER-OUTCOME` lines and records who is actually answering in `state/reviewer-availability.json`: a reviewer that declares a skip is parked for `RUNNER_REVIEWER_SKIP_COOLDOWN_HOURS` (6), and one that times out silently on a full-budget wait is parked after `RUNNER_REVIEWER_SILENT_STRIKES` (2) consecutive cycles, because one silence is noise and two is a pattern. Only a full-budget silence counts: the 1-minute quick passes time out on reviewers that are merely queued, so their silences would park a working reviewer within about ten minutes. Parked reviewers are passed to the gate as `WAIT_FOR_REVIEWS_SKIP`, so a cycle stops spending the whole 20-minute wait on a bot that was never coming. The two clocks are separate — the park window says "do not wait", the strike window says "these silences still count" — because collapsing them lost the strike count: a single silence wrote a window that had already expired and the record was pruned before the next cycle could increment it. Skipping the wait is safe because unresolved review threads still block the merge through required conversation resolution, so a reviewer that answers late with findings still stops it: the runner stopped waiting, it never stopped checking.
- **An unreadable review state is not a review verdict.** The gate exits 3 when it cannot read review state or review threads at all, and the runner retries without dispatching a mission. Before this, a failed thread query produced an empty list, which read as "zero unresolved threads" and would have let a PR merge with its review threads unverified — a false pass, and the most dangerous shape of the bug. Exit 3 is deliberately distinct from exit 1: "the reviewers could not be asked" says nothing about the code, while "unresolved threads exist" is a mission worth dispatching.
- **Notification discipline:** every email that can recur with a persistent condition is rate-limited (3 immediate, then one per 24h per subject). Success emails stay one-shot. Recovery stashes are named, and repeated main-repo recovery reuses the existing `runner-backup-*` branch instead of minting one per cycle. A `--dry-run` records no send at all: `send_email` already suppresses delivery, so a recorded mark would spend the budget on an email nobody received and hide the real alert for a cooldown window.
- **Delivery needs an entry point, not an import:** `send_email` delivers only when the file is executed (production runs it via `cron-wrapper.sh`, so `__main__` holds) or when a test sets `EMAIL_DELIVERY_ENABLED`. Tests import the module, so before this guard any test that exercised an email path mailed the maintainer on every run — issue #1218's Dependabot test did, repeatedly. The few tests that assert delivery opt in explicitly, and `EmailDeliveryGuardTests` pins both directions.
- **Bounded state:** `state/` is swept at startup — `issue-*`, `pr-*`, `quota-*`, `worktree-*`, and `opencode-poisoned-*` files older than `RUNNER_STATE_MAX_AGE_DAYS` (90 default) are deleted, except state for the issues and PRs a live worktree still owns — a `pr-<N>-coderabbit-gate.json` is named by PR number while its worktree is named by issue number, so each prefix is compared against the numbers of its own kind. `reviewer-availability.json` matches no sweep prefix and is deliberately long-lived; it expires its own entries as they are read. `rate-*` files keep their own 24h pruning; logs are rotated at 7 days by `cron-wrapper.sh`.
- **Distinct run logs:** `cron-wrapper.sh` names each log `run_<timestamp>_<mode>_<pid>.log`. The intake and babysit timers can fire in the same minute, so a timestamp-only name made two processes append to one file — interleaved output, duplicated banners, and an exit line reporting the other run's duration.
- **Session poisoning:** an overflowed opencode session that cannot be archived (locked DB) is marked poisoned in state and never resumed again, breaking the resume → overflow → fail cycle.
- **Preference wipe guard:** `--refresh-models` refuses to rewrite `AGENT_PREFERENCES.md` when model discovery fell back entirely to `default` (outage/credential expiry), so transient failures cannot destroy priorities or re-enable disabled models.

## Jev gate (TypeSafe reflex layer)

`.zipper-runner/jev_gate.py` adds advisory TypeSafe (Jev) judgments to the runner loop. Set `TYPESAFE_API_KEY` in `.zipper-runner/.env` to enable; without it every judgment returns `None` and the runner keeps its deterministic behavior.

- **CI failure triage:** failed checks are classified real_regression / flaky / environment / dependency / unrelated (one bounded Jev request per PR failure). All-flaky/infra failures with rerun budget left auto-rerun the failed jobs (`gh run rerun --failed`) instead of burning agent tokens; anything else goes to babysit with the triage attached. Rerun budget: 1 per PR (state file `state/pr-<N>-rerun.json`).
- **Completion verification:** after a babysit success, Jev scores the branch diff against the issue body; a low score sends a rate-limited advisory email (never blocks).
- **Stuck classification:** on agent failure, Jev classifies the output tail (progressing / repeating / blocked / wrong_direction); stuck classes trigger the same fallback path as the repeated-line heuristic, and the retry prompt says what the previous attempt looked like.
- **Prompt-injection gate:** before dispatching a new issue, Jev scores the issue text for injection/jailbreak attempts. High confidence blocks pickup (marker file `state/issue-<N>-injection.json`, rate-limited email; delete the marker to re-enable pickup). Uncertain signals proceed with an advisory email. Fails open — existing mitigations (trusted-author comment filter, `<issue-data>` wrapper in the mission prompt) stay in place.

The gate never writes to GitHub and never grants permissions; `runner.py` owns every enforcement decision.

Tests: `cd .zipper-runner && python3 tests/test_jev_gate.py`

## Architecture: Why two files?

The pipeline is split into a shell script (`.sh`) and a Python script (`.py`) to enforce a strict **Separation of Concerns**.

### 1. `cron-wrapper.sh` (The Environment Bootstrapper)
When the Linux `cron` daemon runs a background job, it executes in a completely "naked" environment. It does **not** load user profiles (`~/.bashrc`, `~/.profile`).
* If Python were executed directly by cron, tools like `dotnet`, `gh`, and `agy` would instantly fail because they wouldn't be in the system's restricted `$PATH`.
* The bash script exists purely to construct the proper environment (injecting `PATH`, `HOME`, `DOTNET_ROOT`), manage log directory creation, handle log rotation, and safely route output to timestamped files.

### 2. `runner.py` (The Brain / Orchestrator)
While Bash is excellent for setting up environments, it is notoriously fragile when handling JSON, complex conditionals, and state management.
* The runner needs to query the GitHub API via `gh pr view --json`, parse arrays of CI checks, compute time differences for hanging checks, and safely acquire file locks (`runner.lock`) to prevent concurrent executions.
* Implementing this logic in Bash would require a fragile mess of `jq` queries and convoluted `if/else` blocks. Python handles these complex API interactions and logic workflows cleanly and robustly.

## Configuration

Native checkout paths are resolved relative to the scripts. Override `RUNNER_BASE`, `REPO_PATH`, `WORKTREES_BASE`, `DOTNET_ROOT`, and `EMAIL_RECIPIENT` for another installation. Keep credentials in the ignored `.env` or the process environment. GitHub repository endpoints remain Zipper-specific.
